## 8️⃣ Persistence & Crash Safety

| Scenario | Behaviour |
|----------|-----------|
| Normal close | TTrayForm.FormDestroy → SaveAllNotes (flush autosave) → SettingsController.SaveSettings → BackupService not auto‑run. |
| Windows shutdown | Same as normal close (VCL receives WM_QUERYENDSESSION → Application.Terminate). |
| Application crash | Any note edited since last autosave flush (≤ 1 s) lost because JSON written only on autosave timer or explicit SaveNote. No transaction log. |
| Power loss | Same as crash – last autosave may be up to 1 s old. |
| Multiple notes edited simultaneously | Each note has its own autosave timer (shared service but single pending note). Rapid edits on different notes could cause the later note to overwrite pending note → possible loss for the first note. |
| Storage unavailable | SaveNote returns False; UI does not react (no error dialog). Autosave timer will keep retrying on next tick. |
| Corrupted JSON | Skipped silently on load – note disappears without warning. |
| Autosave | Debounced 1 s (configurable). Triggered on memo change, drag move, resize. Implementation uses a single pending note – race condition noted above. |

Risk – Data loss possible on crash / power loss; no write‑ahead log, no atomic replace.

## 2️⃣2️⃣ Final Executive Report

### Application Overview
Sticky Notes is a lightweight, tray‑based desktop utility written in Delphi 11 (VCL). It lets users create multiple border‑less sticky‑note windows, each with a coloured header, plain‑text memo, and basic window behaviours (drag, resize, collapse, pin, lock). Notes are persisted as individual JSON files under %APPDATA%\StickyNotes\notes\; settings live in an INI file. The app registers a global hot‑key (Ctrl+Alt+N) for quick note creation, supports auto‑start, light/dark VCL styles, and ZIP‑based backup/restore.

### Current Architecture
A controller‑centric design with a clear but shallow layering:

* Views – four VCL forms (tray host, note, settings, about).
* Controllers – TNoteManager, TSettingsController, TTrayController (unused).
* Domain – TNote, TSettings, enums.
* Persistence – INoteStorage abstraction; only TJsonStorage functional.
* Services – autosave, hotkeys, backup, theme, startup.
* Utilities – windowing, monitor, colour, JSON, ISO‑8601 helpers.

The hidden TTrayForm acts as the composition root, instantiating every service and wiring events. This creates a god‑form anti‑pattern.

### Biggest Strengths (Top 5)
1. Clean storage abstraction – swapping JSON ↔ SQLite is trivial.
2. Per‑note JSON files – simple, human‑readable, easy to sync with cloud folders.
3. Modular service layer – autosave, hotkeys, backup, theme are isolated.
4. Multi‑monitor aware positioning – uses MonitorFromWindow / work‑area constraints.
5. Zero external dependencies – pure Delphi/RTL, no third‑party binaries.

### Biggest Problems (Top 10, severity)
| # | Problem | Severity |
|---|---------|----------|
| 1 | God form TTrayForm – tight coupling, hard to test | 🔴 |
| 2 | Autosave single‑pending‑note race condition | 🟠 |

| 8 | SQLite storage stub dead code | 🟢 |
| 9 | Settings stored in INI while notes use JSON (inconsistent) | 🟡 |
|10| UI not fully theme‑aware (flat header buttons) | 🟡 |

### Biggest Risks
* Data loss on crash/power‑loss (autosave race, non‑atomic writes).
* Maintainability – central god form makes future changes risky.
* Compatibility – lack of DPI awareness leads to blurry UI on Win10/11 scaling.
* Security – plain‑text notes, no encryption.

### Modernization Opportunities (Top 10)
1. Add high‑DPI manifest and scale all constants.
2. Refactor to dependency‑injected application service (remove god form).
3. Atomic JSON writes + versioned schema + migration.
4. Per‑note autosave queue (or debounced per note).

7. Rich‑text / Markdown support (replace TMemo).

### Overall Assessment
Score: 5.5 / 10 – functional and reasonably clean for a hobby‑size Delphi app, but suffers from architectural centralisation, DPI ignorance, and data‑safety gaps. With the phased roadmap it can become a robust, modern sticky‑note product.

## 8️⃣ Persistence & Crash Safety

| Scenario | Behaviour |
|----------|-----------|

| Corrupted JSON | Skipped silently on load – note disappears without warning. |
| Autosave | Debounced 1 s (configurable). Triggered on memo change, drag move, resize. Implementation uses a single pending note – race condition noted above. |

Risk – Data loss possible on crash / power loss; no write‑ahead log, no atomic replace.

## 2️⃣2️⃣ Final Executive Report

### Application Overview
Sticky Notes is a lightweight, tray‑based desktop utility written in Delphi 11 (VCL). It lets users create multiple border‑less sticky‑note windows, each with a coloured header, plain‑text memo, and basic window behaviours (drag, resize, collapse, pin, lock). Notes are persisted as individual JSON files under %APPDATA%\StickyNotes\notes\; settings live in an INI file. The app registers a global hot‑key (Ctrl+Alt+N) for quick note creation, supports auto‑start, light/dark VCL styles, and ZIP‑based backup/restore.

### Current Architecture
A controller‑centric design with a clear but shallow layering:

* Views – four VCL forms (tray host, note, settings, about).
* Controllers – TNoteManager, TSettingsController, TTrayController (unused).
* Domain – TNote, TSettings, enums.
* Persistence – INoteStorage abstraction; only TJsonStorage functional.
* Services – autosave, hotkeys, backup, theme, startup.
* Utilities – windowing, monitor, colour, JSON, ISO‑8601 helpers.

The hidden TTrayForm acts as the composition root, instantiating every service and wiring events. This creates a god‑form anti‑pattern.

### Biggest Strengths (Top 5)
1. Clean storage abstraction – swapping JSON ↔ SQLite is trivial.
2. Per‑note JSON files – simple, human‑readable, easy to sync with cloud folders.
3. Modular service layer – autosave, hotkeys, backup, theme are isolated.
4. Multi‑monitor aware positioning – uses MonitorFromWindow / work‑area constraints.
5. Zero external dependencies – pure Delphi/RTL, no third‑party binaries.

### Biggest Problems (Top 10, severity)
| # | Problem | Severity |
|---|---------|----------|
| 1 | God form TTrayForm – tight coupling, hard to test | 🔴 |
| 2 | Autosave single‑pending‑note race condition | 🟠 |
| 3 | No high‑DPI awareness (manifest, hard‑coded pixels) | 🟠 |
| 4 | Silent error swallowing in storage & backup | 🟠 |
| 5 | Non‑atomic JSON writes – corruption risk on crash | 🟠 |
| 6 | No automated tests (unit / integration) | 🟠 |
| 7 | Duplicate colour constants & magic numbers | 🟡 |
| 8 | SQLite storage stub dead code | 🟢 |
| 9 | Settings stored in INI while notes use JSON (inconsistent) | 🟡 |
|10| UI not fully theme‑aware (flat header buttons) | 🟡 |

### Biggest Risks
* Data loss on crash/power‑loss (autosave race, non‑atomic writes).
* Maintainability – central god form makes future changes risky.
* Compatibility – lack of DPI awareness leads to blurry UI on Win10/11 scaling.
* Security – plain‑text notes, no encryption.

### Modernization Opportunities (Top 10)
1. Add high‑DPI manifest and scale all constants.
2. Refactor to dependency‑injected application service (remove god form).
3. Atomic JSON writes + versioned schema + migration.
4. Per‑note autosave queue (or debounced per note).
5. Full dark‑mode styling for custom header buttons.
6. Automated test suite (DUnitX) + CI.
7. Rich‑text / Markdown support (replace TMemo).
8. Tagging & full‑text search (SQLite FTS or in‑memory index).
9. Windows 11 toast notifications & jump‑list.
10. Optional encryption for sensitive notes.

### Recommended Target Architecture
(See diagram in §1️⃣8️⃣) – a clean Presentation → Application Services → Domain → Persistence flow with a tiny DI container, logging, and configuration abstractions.

### Recommended Roadmap
Follow the Phase 0‑8 plan in §2️⃣0️⃣ – start with reliability (atomic writes, autosave fix, logging), then architectural decoupling, then DPI/theme, then Windows integration, then search/organisation, then advanced features, finally testing & installer.

### Estimated Complexity
Medium – the codebase is modest (~30 units) but the god‑form and lack of tests mean a significant refactor (≈ 2‑3 person‑weeks) before new features can be added safely.

### Overall Assessment
Score: 5.5 / 10 – functional and reasonably clean for a hobby‑size Delphi app, but suffers from architectural centralisation, DPI ignorance, and data‑safety gaps. With the phased roadmap it can become a robust, modern sticky‑note product.
